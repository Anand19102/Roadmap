# 📄 RESUME EVOLUTION

> **Purpose:** Build the resume continuously as the user's skills, projects, internship experience and achievements develop.
>
> The resume is **not** a document created at the end of placement preparation.

---

# 1. CORE PRINCIPLE

The resume evolves alongside the roadmap.

```text
Learning
   ↓
Practice
   ↓
Projects
   ↓
Evidence
   ↓
Resume bullet
   ↓
Interview story
```

Every important achievement should eventually produce usable evidence.

---

# 2. RESUME STRATEGY

The primary professional identity developed through this roadmap is:

> **Software Engineer → Backend Engineer**

```text

```

Supporting skills:


# 10. PROJECT BULLET RULE

Every project should eventually answer:

### What did you build?

### Why did you build it?

### What technical problem did you solve?

### How did you solve it?

### What technologies were used?

### What measurable result can be stated?

Strong bullet structure:

```text
Action + Technical Implementation + Purpose/Result
```

Avoid:

> Made a Spring Boot project using Java.

Prefer a factual engineering description such as:

> Developed a Spring Boot REST API for X, implementing Y and Z to support A.

Only include claims that are actually true.

---

# 11. NO FAKE METRICS

Never invent:

* users
* performance improvements
* percentages
* response-time improvements
* traffic
* accuracy
* scalability
* business impact

If there is no real measurement:

Describe the implementation instead.

# 13. EXPERIENCE

When internship experience becomes available:

Create:

* company
* role
* duration
* technologies
* responsibilities
* measurable contributions
* major technical work
* STAR stories

Never merely list the company name.

The experience must become explainable interview evidence.

# 15. SKILLS SECTION

Skills are divided into:

## Tier A — Strong / Interview-Ready

Technologies that can be discussed deeply.

## Tier B — Working Knowledge

Technologies that can be used but are not yet deep.

## Tier C — Familiarity

Technologies understood at a basic level.

Only appropriate skills should reach the final resume.

---

# 16. RESUME SKILL RULE

> **If an interviewer can reasonably ask a follow-up question about it, be prepared to answer that follow-up.**

Therefore:

Do not list technologies merely because:

* they appeared in a tutorial
* they were used once
* they were copied into a project
* an AI tool generated the code
* they sound impressive

---

# 17. RESUME ↔ PROJECT CONSISTENCY

Everything on the resume should be traceable to evidence.

```text
Resume skill
      ↓
Project / coursework / experience
      ↓
Actual code
      ↓
Actual understanding
```

If the chain breaks, remove or downgrade the claim.

---

# 19. RESUME REVIEW CHECKPOINTS

Review the resume:

* after major project completion

* before placement season
* after internship

---

# 20. FINAL RESUME QUALITY CHECK

Before using a resume:

### Accuracy

* Every claim is true.

### Relevance

* Skills match the target role.

### Evidence

* Projects support the claims.

### Clarity

* Bullets are understandable.

### Technical depth

* Listed technologies can be discussed.

### Consistency

* GitHub/projects/resume tell the same story.

### Conciseness

* No unnecessary content.

# 22. GOLDEN RULE

The final resume should be the **compressed representation of the journey**, not a collection of technologies the user hopes to learn.

```text
Learn → Build → Understand → Measure → Explain → Document → Resume
```
