# 📝 NOTE-TAKING SYSTEM

> **Purpose:** Prevent excessive note-taking while ensuring important knowledge is retained and reusable.

---

# 1. THE PROBLEM

Too many notes create:

* duplicated information
* huge documents
* difficult revision
* false productivity
* reduced coding time

The objective is therefore:

> **Maximum useful knowledge with minimum unnecessary writing.**

---

# 2. THE THREE-TIER NOTE SYSTEM

All major learning will use three complementary layers:

```text
TIER 1 — HANDWRITTEN / ACTIVE NOTES
TIER 2 — DIGITAL REFERENCE NOTES
TIER 3 — CODE / IMPLEMENTATION
```

See `06_THREE_TIER_NOTES.md` for the complete system.

---

# 3. NOTES SHOULD ANSWER QUESTIONS

Good notes should allow you to answer:

* What is this?
* Why does it exist?
* How does it work?
* When do I use it?
* What are the important rules?
* What are common mistakes?
* What should I remember?

---

# 4. DO NOT TRANSCRIBE VIDEOS

Never turn a lecture into a transcript manually.

Do not write:

> "The instructor says..."

Instead convert the information into concise learning notes.

---

# 5. NOTE PRIORITY

## HIGH VALUE

Write:

* definitions
* core concepts
* formulas
* rules
* invariants
* complexity
* important diagrams
* patterns
* common mistakes
* interview points

## MEDIUM VALUE

Write:

* useful examples
* implementation details
* comparisons
* edge cases

## LOW VALUE

Usually do not write:

* motivational talk
* repeated examples
* obvious syntax
* conversational explanations
* jokes
* redundant explanations

---

# 6. TRANSCRIPT-ASSISTED NOTES

When useful, transcripts may be used to accelerate note extraction.

But:

> **Transcript ≠ final notes.**

The process is:

```text
Video
↓
Transcript
↓
Extract important ideas
↓
Condense
↓
Verify understanding
↓
Create final notes
```

Never paste an entire transcript into the notes folder as a substitute for learning.

---

# 7. CODE IS ALSO A NOTE

For programming topics, the actual implementation is often more valuable than several pages of explanation.

Maintain clean code examples.

Example:

```text
binary-search/
├── README.md
├── BinarySearch.java
├── variations.md
└── mistakes.md
```

---

# 8. NOTE STRUCTURE

A good technical topic note should generally contain:

```markdown
# Topic

## 1. What is it?

## 2. Why does it exist?

## 3. Core idea

## 4. Important rules

## 5. Implementation

## 6. Complexity

## 7. When to use

## 8. When not to use

## 9. Common mistakes

## 10. Examples

## 11. Interview points
```

Not every topic requires every heading.

---

# 9. NOTES VS MEMORY

Do not attempt to memorize everything.

Notes are an **external memory system**.

The goal is to memorize only high-frequency/high-value information.

---

# 10. REVISION-FRIENDLY NOTES

A note should be understandable after several weeks.

Avoid notes such as:

> "This thing works like what he said."

Instead write enough context that future-you understands it.

---

# 11. NOTE QUALITY TEST

Before considering a note complete, ask:

> "If I open this six months from now, can I understand it without watching the original video?"

If yes → good.

If no → improve the note.

---

# 12. THE GOLDEN RULE

> **Notes should support learning and revision—not replace learning and coding.**
